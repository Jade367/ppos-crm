## Goal

The repo can start a local Supabase stack from `supabase/config.toml`, apply one foundation migration (extensions `pg_cron` + `pg_net`, trigger function `public.set_updated_at()`), load a fake-data seed, and run pgTAP tests, including nested folders. The golden meta-test is installed, so from now on any table without RLS and any `SECURITY DEFINER` function without a pinned `search_path` fails CI for the life of the project. ADR-0001 fixes the migration workflow every later database task follows.

## Spec

1. **CLI**: `npm view supabase version` → `pnpm add -Dw supabase@<that exact version>`. Use `pnpm exec supabase …` for every command in this task so the pinned CLI is used. Check: `pnpm exec supabase --version`.
2. **Init**: at the repo root, run `pnpm exec supabase init --help` first and pass the flags it lists to decline editor settings ([H] e.g. `--with-vscode-settings=false --with-intellij-settings=false`); if there are none, run `pnpm exec supabase init < /dev/null`. Never wait on an interactive prompt. Acceptance 11 proves no `.vscode/` was committed.
3. **`config.toml`** edits only:
   - `project_id = "ppos-takeaway"` (names the local containers, e.g. `supabase_db_ppos-takeaway`).
   - `[db] major_version` = the DEV project's Postgres major from `environments.md`. If it is not recorded there, keep the generated value and add a Follow-up.
   - `[db.seed]`: `enabled = true`, `sql_paths = ["./seed.sql"]`.
   - Keep default ports (API 54321, DB 54322, Studio 54323). Leave every other section as generated.
4. **Migration `<ts>_foundation.sql`** (idempotent, commented, no tables, no policies, no grant changes):
   - Create `pg_cron` and `pg_net` with the exact statements in the current Supabase docs for each extension (read them with the web-reader tool; cite the URLs in ADR-0001). Use `if not exists`.
   - `public.set_updated_at()`: `returns trigger`, `language plpgsql`, `set search_path = ''`, body `new.updated_at := now(); return new;`. Security invoker (the default). A comment shows how later tables attach it: `create trigger set_updated_at before update on public.<table> for each row execute function public.set_updated_at();`.
5. **`seed.sql`**: a header comment only: `-- DEV SEED ONLY. Fake data: example.com emails, 07700 900xxx phone numbers. Never real customers, shops or staff.` No inserts yet (tables arrive in P1-05). ASCII only (`cjk-lint` scans this file).
6. **`supabase/tests/foundation.test.sql`** (pgTAP; `begin;` … `select * from finish(); rollback;`; `select plan(n);` with the exact count):
   - `ok(exists(select 1 from pg_extension where extname = 'pg_cron'), …)` and the same for `pg_net`;
   - `has_function('public', 'set_updated_at', …)`;
   - behaviour: `create temp table t (id int primary key, updated_at timestamptz not null default '2000-01-01');` + a `before update` trigger using `public.set_updated_at()`; insert, update, then `ok((select updated_at > '2000-01-01' from t), …)`.
   - Never use pgTAP `skip()` or `todo()` (guard `pgtap-skip`).
7. **Golden test**: `pnpm acceptance:install P0-02`. It must show up in the `supabase test db` output. Do not edit it; the guard `acceptance-integrity` checks it byte for byte. It is a meta-test: it PASSES on the empty foundation database, so AGENTS.md §2 step 4 ("confirm they fail") does not apply here; Spec 8 is the proof that it can fail.
8. **Gate proofs** (local only, nothing committed; check the container name with `docker ps`): (a) with the stack running, `docker exec supabase_db_ppos-takeaway psql -U postgres -d postgres -c 'create table public.tmp_no_rls (id int);'` → `pnpm exec supabase test db` must FAIL on `every table in schema public has row level security enabled`; then `… -c 'drop table public.tmp_no_rls;'` → PASS again. (b) `… -c "create function public.tmp_sd() returns int language sql security definer as 'select 1';"` → `pnpm exec supabase test db` must FAIL on `every SECURITY DEFINER function in schema public pins search_path`; then `… -c 'drop function public.tmp_sd();'` → PASS again. Paste all four results into PROGRESS.md.
9. **`verify-extra.mjs`**: confirm both database branches behave as written in P0-01 (stack running → tests + lint run; stack stopped → `SKIPPED (no local supabase)`). If `supabase status` does not signal "not running" through its exit code, fix `scripts/dev/verify-extra.mjs` (not protected) and record what you observed.
10. **ADR-0001** `docs/takeaway/adr/0001-migrations.md` — headings: Status (`Proposed`), Context, Decision, Consequences, Evidence (commands + output excerpts). The Decision must state:
   - create migrations only with `supabase migration new <snake_description>` → `<UTC timestamp>_<snake_description>.sql`; never edit a migration once it is on `main` (hook + CI enforce append-only);
   - local loop: `supabase start` → `supabase db reset` (local only) → `supabase test db` → `supabase db lint --level error`;
   - every table enables RLS in the same migration that creates it (golden meta-test); every `SECURITY DEFINER` function has `set search_path = ''`; every policy gets pgTAP tests for allow **and** deny;
   - own status columns: `text` + `CHECK`; Stripe-owned enums: plain `text`; money: integer `_pence` with `CHECK (… >= 0)`;
   - backward-compatible changes: expand → deploy code → contract in a later migration;
   - from P1-05 on, every migration task regenerates `packages/core/src/db/database.types.ts` with `supabase gen types typescript --local`;
   - who may push where: agent → local, and DEV via `supabase db push` only after the human has linked DEV; PROD → human or CI only;
   - test layout: `supabase/tests/*.test.sql` (own tests), `supabase/tests/rls/` (policy tests, P1-05), `supabase/tests/acceptance/` (golden, installed only by `pnpm acceptance:install`);
   - `seed.sql` holds fake data only;
   - the extension statements and their doc URLs.

## Acceptance

1. `pnpm acceptance:install P0-02` → prints `installed supabase/tests/acceptance/rls_enabled.test.sql`
2. `pnpm exec supabase start` → exit 0 (Docker must be running)
3. `pnpm exec supabase db reset` → exit 0; output shows the foundation migration applied and `seed.sql` loaded
4. `pnpm exec supabase test db` → lists `acceptance/rls_enabled.test.sql` and `foundation.test.sql`, each `ok`; ends with `All tests successful.` and `Result: PASS`
5. Both gate proofs from Spec 8 → each first run FAILS naming its assertion, each second run PASSES
6. `pnpm exec supabase db lint --level error` → exit 0
7. Stack running: `pnpm verify` → exit 0 and the output shows `supabase test db` ran (no `SKIPPED (no local supabase)`)
8. `pnpm exec supabase stop` then `pnpm verify` → exit 0 and prints `SKIPPED (no local supabase)`
9. `ls supabase/migrations` → exactly one file, matching `^[0-9]{14}_foundation\.sql$`
10. `node scripts/guards/run-all.mjs` → `All guards passed.`
11. `git ls-files supabase .vscode` (after committing) → only `supabase/.gitignore`, `supabase/config.toml`, the migration, `supabase/seed.sql`, `supabase/tests/foundation.test.sql`, `supabase/tests/acceptance/rls_enabled.test.sql`
12. After `pnpm install --frozen-lockfile`, `pnpm exec supabase --version` prints the pinned version (proves the binary download was not skipped)

## Stop and escalate if

- Docker is not installed or not running (`docker info` fails) → BLOCKED; the human starts Docker Desktop.
- `supabase test db` does not run the file in `supabase/tests/acceptance/` → BLOCKED. Do not move or copy the golden file.
- The golden test fails on a database with zero tables → BLOCKED with the full output. Never change the test.
- `pg_cron` or `pg_net` cannot be created locally with the documented statements, or `db lint` reports errors inside Supabase-owned schemas.
- The `supabase` npm package cannot install its binary without an interactive approval or a protected-file change → BLOCKED; say which.
- Any command you are about to run would touch a linked or remote project.

## Hints (verified facts / pitfalls)

- The golden test checks two catalog invariants: every `public` table has `relrowsecurity`, and every `public` `SECURITY DEFINER` function has `search_path=` in `proconfig`. It creates the `pgtap` extension in schema `extensions` itself.
- `supabase start` downloads Docker images on first run (several minutes). `supabase status` prints local URLs and local demo keys; never paste remote keys anywhere.
- Local database URL: `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.
- `supabase db reset` rebuilds the local database from migrations + seed. `supabase db reset --linked` is hook-blocked and must never be attempted.
- `now()` is constant inside one transaction, so the behaviour test compares against a default far in the past instead of comparing two `now()` values.
- [H] Supabase docs have shown `create extension if not exists pg_cron with schema pg_catalog;` and `create extension if not exists pg_net with schema extensions;`. Verify against the current pages before using them.
- [H] pnpm ≥ 10 does not run dependency install scripts by default, and the `supabase` npm package uses one to fetch its binary. Allow it with the non-interactive setting documented for the installed pnpm major (pnpm 10: `onlyBuiltDependencies` in `pnpm-workspace.yaml` or in the root `package.json` `pnpm` field). Verify with `pnpm exec supabase --version`.
- CI installs the CLI with `supabase/setup-cli@v1` and `version: latest`, which may differ from your pinned version. Record yours; the human pins CI (your `## Proposed doc changes` entry).
- Append-only applies to migrations already on `main`. Before merge you may still edit your own new migration on this branch.
- The `pgtap-skip` guard flags the words `skip(` and `todo(` anywhere under `supabase/tests/`, including comments.
